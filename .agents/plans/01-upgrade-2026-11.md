## 0. Ground rules for executing this plan

- **Branch:** `chore/upgrade-2026-11`, created from the current working tree, including the uncommitted partial upgrade, which is the starting point.
- **One commit per phase.** The user approved committing at phase boundaries. Stage only the files you intend to commit, and never commit `.env`, `.wrangler/`, `.cloudflare/`, `db-copy/`, `dist/` or `.fallow/`.
- **End-of-phase gate:**
  1. `pnpm biome check --write <changed paths>`
  2. typecheck (`pnpm tsc --noEmit`; from Phase 2 on, `pnpm typecheck`)
  3. `pnpm build`
  4. tests, from Phase 6 on: `pnpm test`
  5. `pnpm test:smoke` against the dev server
  6. `fallow audit --format json --quiet --base main`, then report the verdict and any new findings

  If a step fails, fix it or stop and report it. Never claim a phase is done while its gate fails.
- **Remote and live resources: ask first.** That includes the remote D1 database (`irishette-dev`), deploys, secrets, and live-mode Stripe. Only the Stripe **sandbox** is in use.
- **Local D1 data is disposable.** The user approved wiping and reseeding it.
- **`db-copy/` contains real personal data.** Never read it into seeds, commit it, or edit it.
- **Use the installed skills:**
  - Cloudflare work: `cf-cli`, `wrangler`, `workers-best-practices`, `workers-development`.
  - Stripe work: `stripe-best-practices`, `upgrade-stripe`, `stripe-docs`.
  - Review: `fallow`, `fallow-review`.
  - TanStack: read the skills under `node_modules/.pnpm/@tanstack+*/node_modules/@tanstack/*/skills/`, and re-read them after upgrading TanStack.
- **Do not** introduce Hono, Effect, ESLint or Prettier during this plan.

## 1. Decisions record (agreed with the user)

| Topic | Decision |
|---|---|
| Backend | Keep TanStack Start server routes (`src/routes/api/*`) + tRPC. **No Hono.** |
| Starting point | Use the existing uncommitted partial upgrade as the baseline; fix it first. |
| Major bumps in scope | Stripe SDKs, react-day-picker 10, TanStack Table 9, TypeScript 7, swiper 14, nanoid 6, Vitest 5, `@types/node` 26. **Remove** `web-vitals` (unused). |
| tRPC vs server functions | tRPC stays the API. Add a per-request **SSR caller** (local link, no HTTP). Server functions are used for auth/session and Start-specific needs only. |
| Security fixes | Done **after** the upgrades (Phase 7). Structural SSR/session fixes land in Phase 5. |
| Cloudflare tooling | Migrate to the **`cf` CLI + `cloudflare.config.ts`** (beta) with `@cloudflare/vite-plugin@beta`. Remove `wrangler.jsonc` and `worker-configuration.d.ts`. Deploy only via `cf deploy`. Phase 2 has a go/no-go check. |
| Local state | Wipe build dirs and local D1/KV and start fresh. Seed with synthetic data. |
| Stripe | Latest SDK and API version (`stripe` 23.1.0 → `2026-10-28.endive`). **Charge immediately**, and refund automatically if confirmation fails. |
| Auth | Session state comes from a **TanStack server function + TanStack Query hook** (`useSession`). Protected routes move under pathless `_authed` / `_authed/_admin` layouts. |
| Tests | Add Vitest (unit + Workers), a smoke script and a few Playwright E2E tests. |
| `daysOfWeek` | **Remove completely** (unused, no UI, buggy). Pricing rules use start/end dates only. |
| Pricing rules | Inclusive start/end. Each night priced independently: rule price if a rule covers the night, else base price. Single-night rules (start = end) allowed. **Active rules may not overlap**; the API returns `CONFLICT` with the conflicting rule. Inactive rules are excluded from the check; **reactivation re-checks** and errors. Precedence = earliest `activated_at`. |
| Guest surcharge | **Removed** (the "more than 4 guests costs 10% more" rule). |
| Max guests | `room.max_guests` in the DB (default 2). Admins can change it via a procedure and UI. Enforced on booking. |
| Booking overlap | Same-day turnover allowed: `newIn < existing.out AND newOut > existing.in`. |
| Admin blocks | Inclusive start/end. The block's last day is **not** available for check-in. Check-out on the block's first day **is** allowed. Conflict if `in <= block.end AND out > block.start`. |
| Blocks vs bookings | Creating or updating a block over a confirmed booking, a non-expired pending booking, or an **imported external** booking throws `CONFLICT` listing the overlapping bookings. |
| iCal export | Per-room **secret token** in the URL. Feed includes **only our confirmed bookings and admin blocks**: no imported external events, no pending bookings. External platforms already sync with each other. |
| iCal import cron | Stay at **every 30 minutes** for now. Evaluate 5 minutes at production go-live. |
| Extra platforms | Vrbo / Booking.com URLs are **pending from the client**. The design must allow adding feeds as data, not code. |
| IDs | **UUIDv7** (TEXT) primary keys on all tables, including Better Auth tables. A **16-char nanoid `public_id`** (`[0-9a-z]`) on every table shown in a dynamic route: `bookings`, `user`, `room`. URLs and frontend lookups use `publicId`. |
| Migrations | Delete `drizzle/` and regenerate **one fresh baseline** with drizzle-kit. Local only. **Remote is untouched** until local works and the user approves. |
| Effect | **Deferred** to a separate plan. The user wants to investigate it for the tRPC backend later (see Appendix C). |

## Appendix A: Date rules reference

Dates are `YYYY-MM-DD` strings. A stay's nights are `[checkIn, checkOut)`.

| Rule | Condition |
|---|---|
| Booking conflicts with booking/hold | `newIn < b.checkOut && newOut > b.checkIn` |
| Booking conflicts with an external event (end exclusive) | `newIn < e.end && newOut > e.start` |
| Booking conflicts with an admin block (inclusive) | `newIn <= blk.end && newOut > blk.start` |
| Night `n` priced by a rule (inclusive) | `rule.start <= n && n <= rule.end` |
| Active rules overlap (forbidden) | `a.start <= b.end && b.start <= a.end` |
| Block conflicts with a booking (for the admin error) | `blk.start < b.checkOut && blk.end >= b.checkIn` |
| Calendar check-in disabled on day `d` | `d` is a booked night, an external event night, or within `[blk.start, blk.end]` |
| Calendar check-out allowed on day `d` | `d` can equal another booking's check-in or a block's start, if no unavailable night lies in `[checkIn, d)` |

Examples:
- **Block Jun 8–10:** check-in Jun 10 ✗, Jun 11 ✓; stay Jun 7–8 ✓; stay Jun 7–9 ✗.
- **Rule Jun 8–10, stay Jun 10–12:** night of Jun 10 = rule price, Jun 11 = base price.

## Appendix C: Deferred, Effect evaluation (separate future plan)
